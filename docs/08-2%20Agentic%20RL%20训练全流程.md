## 1、为什么 Agent RL 比通用 RLHF 更难

### 1.1 三大核心差异

| 维度 | 通用 RLHF（如 ChatGPT 对齐） | Agent RL（Globex 场景） |
|---|---|---|
| Action space | 只有文本生成 | 文本生成 + 工具调用（9 个工具）+ fork 决策 |
| Reward 时机 | 一条回复结束就能评 | 整条轨迹跑完（5-10 轮 Act）才有终极 reward |
| 环境 | 只有模型自身 | 模型 + 工具服务 + 外部 API，每次返回不完全一样 |

### 1.2 三大差异带来的三个工程问题

| 问题 | 根因 | 不解决会怎样 |
|---|---|---|
| **方差大** | 长轨迹里每一步的随机性累积 | 梯度方向不稳，训练震荡 |
| **Credit assignment 难** | 终极 reward 要分配到 5-10 步里的每一步 | 模型不知道哪一步做对了 / 哪一步做错了 |
| **Reward hacking 多** | 工具返回可预测 → 模型找到绕过 reward 的捷径 | 模型表面高分实际无用（如空 Summary） |

这些问题决定了 Globex 不能直接用标准 PPO——需要序列级算法（GSPO）+ 过程奖惩 + 防 hacking 门禁。

## 2、Reward 函数工程化：从概念到公式

### 2.1 五维 reward 的具体计算

第 8 章 §6.2 给了五维 reward 的表格。本节把它们展开成**可计算的定义**。

#### 维度 1：响应质量（R_quality）

```text
R_quality = Rubric_P2_mean / 5.0

其中 Rubric_P2_mean 是 judge 对 P2 三项
（需求覆盖度 / 场景洞察力 / 决策建议价值）的平均分。

P2 每项 1-5 分，归一化到 [0, 1]。
```

#### 维度 2：过程合规（R_process）

```text
R_process = (score_order + score_terminal + score_no_loop) / 3.0

score_order    = 1.0 if 工具调用顺序合法（Planner 在前 / Summary 在末）else 0.0
score_terminal = 1.0 if 最终调用了 ShoppingSummary 或 ChatFallback else 0.0
score_no_loop  = 1.0 if 无同工具连续 >= 4 次 else 0.0
```

#### 维度 3：Query 拆解（R_query）

```text
R_query = BERTScore_F1(
    candidate = Planner 输出的 sub-query 列表拼接,
    reference = 用户原始 query 的需求关键词
)
```

用 BERTScore 而非 BLEU——因为 sub-query 不需要和 query 字面一样，只要语义覆盖到。

#### 维度 4：商品相关性（R_relevance）

```text
R_relevance = 满足约束的商品数 / 推荐商品总数

约束来自 Planner 输出：
price <= budget / material != blacklist / ...

每条约束独立检查，取通过率。
```

#### 维度 5：格式与安全（R_safety）

```text
R_safety = 0.0 if 输出中出现 item_id / 内部工具名 / 违规内容
           1.0 otherwise
```

注：`R_safety = 0` 时直接令整体 `R = -1.0`，一票否决。

### 2.2 归一化 + 加权

```text
R = 0.40 × R_quality
  + 0.20 × R_process
  + 0.15 × R_query
  + 0.15 × R_relevance
  + 0.10 × R_safety

特殊规则：
  if R_safety == 0:  R = -1.0（一票否决）
  if P0 任一项 fail: R = -1.0（Rubric P0 红线）
```

### 2.3 Reward Shaping：终态为主 + 过程合规奖惩为辅

两种极端：

| 策略 | 每步都有 reward | 只有终态 reward |
|---|---|---|
| 优点 | Credit assignment 容易 | 不需要设计中间奖惩 |
| 缺点 | 中间 reward 设计不好会引入偏置 | 方差大、学习慢 |

Globex 的折衷：

```text
终态 reward（R）→ 分配给轨迹最后一步

过程奖惩 → 只在两个地方给：
  - 每次 tool_call 成功执行：+0.01（鼓励尝试）
  - 每次检测到循环（同工具连续 >= 3 次）：-0.05（惩罚）
```

过程奖惩幅度刻意很小（0.01 / -0.05），**不超过终态 reward 的 5%**——否则模型会“刷过程分”而忽略最终质量。

### 2.4 Reward Hacking 三种典型表现 + 防御

| Hacking 表现 | 根因 | 防御 |
|---|---|---|
| 调 ShoppingSummary 但内容为空 | `R_process.score_terminal` 给了 +1 | 加门禁：Summary 文本 < 50 字 → `R = -0.5` |
| 只推 1 件商品避免出错 | 少推 = 少错 = `R_relevance` 高 | 加门禁：推荐数量 < 2 件 → `R_quality` 折半 |
| 把 Rubric 评分维度写进回答取悦 judge | judge 模型看到“评分”关键词倾向给高分 | 加门禁：回答中出现 `P0/P1/P2/Rubric` → `R = -0.5` |

这些门禁不是 loss 的一部分——是在计算 reward 之后，作为**后处理 clip** 加的。

## 3、Rollout 采集与环境交互

### 3.1 Rollout 是什么

```text
Rollout = 用当前 policy 模型在 Agent 环境中跑一批 query，
          收集完整轨迹（state, action, reward）作为 RL 训练的输入。
```

每一轮 RL 训练的流程：

```text
采集 Rollout（花费 70% 时间）
  → 计算 Reward
  → 更新 Policy（花费 30% 时间）
  → 评测
  → 下一轮
```

### 3.2 环境搭建：工具返回的三种模拟策略

| 策略 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| 线上真实调用 | rollout 时真的调 ItemSearch / PriceCompare 等 | 最接近真实 | 慢、不可复现、依赖外部服务 |
| 录制回放 | 把历史工具返回按 `(tool_name, args_hash)` 缓存 | **可复现 + 快 + 不依赖** | 覆盖率有限 |
| 简化模拟器 | 写规则模拟工具返回 | 最快 | 偏离真实分布 |

**Globex 选「录制回放」**——兼顾可复现性和真实性。

### 3.3 录制回放的实现

```python
# app/eval/tool_replay.py
import hashlib
import json
from pathlib import Path

REPLAY_DIR = Path("data/tool_replay_cache")


def _hash_args(tool_name: str, arguments: str) -> str:
    key = f"{tool_name}:{arguments}"
    return hashlib.sha256(key.encode()).hexdigest()[:16]


class ToolReplayEnv:
    """Rollout 环境：工具调用走缓存回放，命中不了才报 miss。"""

    def __init__(self):
        self._cache: dict[str, str] = {}
        self._load_cache()

    def _load_cache(self):
        for p in REPLAY_DIR.glob("*.json"):
            data = json.loads(p.read_text())
            self._cache[data["key"]] = data["result"]

    def lookup(self, tool_name: str, arguments: str) -> str | None:
        key = _hash_args(tool_name, arguments)
        return self._cache.get(key)

    def record(self, tool_name: str, arguments: str, result: str):
        """线上调用后存一份到缓存（离线采集时用）。"""
        key = _hash_args(tool_name, arguments)
        self._cache[key] = result
        path = REPLAY_DIR / f"{key}.json"
        path.write_text(json.dumps({
            "key": key,
            "tool_name": tool_name,
            "arguments": arguments,
            "result": result,
        }, ensure_ascii=False))
```

**录制时机**：线上 Agent 每次真实调用工具后，`monitor` 层顺手调一次 `replay_env.record(...)`。积累 2-4 周就能覆盖 80%+ 的 `(tool_name, args)` 组合。

### 3.4 批量 Rollout 工程

| 参数 | 推荐值 | 说明 |
|---|---:|---|
| 每轮采集轨迹数 N | 256-1024 | 太少 → 梯度方差大；太多 → 采集时间长 |
| 并发度 | 32-64 | vLLM 批推理 + 工具查表并发 |
| 单条轨迹最大轮数 | 15 | 超过 15 轮还没结束 → 强制终止并给 `R=-0.5` |
| 单条轨迹最大 token | 16384 | 对齐 SFT 时的 `max_seq_len` |

```text
每轮 Rollout 时间预算（1024 条，32 并发）：

  LLM 推理：~80% 时间 → 约 30 分钟（vLLM + 4×A100）
  工具查表：~5% 时间 → 秒级
  Reward 计算：~15% 时间 → 约 5 分钟（含调 judge LLM 评分）

  总计：~35-40 分钟 / 轮
```

## 4、GSPO 算法详解

### 4.1 标准 PPO 在 Agent 场景的三大问题

| 问题 | PPO 的原因 | 后果 |
|---|---|---|
| 方差大 | token 级 importance ratio 在长序列下累积 | 梯度方向不稳，训练震荡 |
| Credit assignment 难 | GAE 在 10+ 步的轨迹上衰减过快 | 前几步的决策学不到 reward |
| MoE 不稳定 | token 级梯度让专家路由频繁跳变 | 训练崩塌 |

### 4.2 GSPO 的三个核心改进

#### 改进 1：序列级重要性比率

标准 PPO 对每个 token 算 ratio：

```text
r_t = π(a_t|s_t) / π_old(a_t|s_t)
```

GSPO 改为整条序列的 geometric mean：

```text
r_seq = ( Π_{t=1}^{T} π(a_t|s_t) / π_old(a_t|s_t) ) ^ (1/T)
```

**好处**：长序列不会让 ratio 指数增长或缩小，梯度幅度更稳定。

#### 改进 2：Group 采样

同一个 query 跑 G 条轨迹（`G=4-8`），组内做比较：

```text
对同一个 query q：

  生成 G 条轨迹 [τ_1, τ_2, ..., τ_G]
  计算各自 reward [R_1, R_2, ..., R_G]

  组内归一化：
  Advantage_i = (R_i - mean(R)) / std(R)
```

**好处**：不需要额外的 value network（PPO 需要），也不需要 GAE 来估计优势——直接用组内排名。

#### 改进 3：优势估计简化

```text
Advantage(τ_i) = (R_i - mean(R_group)) / (std(R_group) + ε)
```

没有 GAE 的指数衰减问题，所有步都用同一个 advantage——credit assignment 交给“哪条轨迹更好”的组内比较来解决。

### 4.3 和其它算法的对比

| 算法 | 重要性比率 | 优势估计 | 是否需要 value net | Agent 长序列友好度 |
|---|---|---|---|---|
| PPO | token 级 | GAE | 需要 | 差 |
| GRPO | 序列级 | 组内归一化 | 不需要 | 好 |
| **GSPO** | 序列级 | 组内归一化 | 不需要 | **最好（MoE 友好）** |
| DPO | — | 偏好对（两条） | 不需要 | 中（只能两两比） |
| REINFORCE | 序列级 | 减基线 | 不需要 | 中（方差大） |

GSPO 在 GRPO 基础上加了「几何平均比率」和「clip 的平滑版本」，对 MoE 模型更稳。

### 4.4 核心超参

| 超参 | 推荐值 | 说明 |
|---|---:|---|
| `group_size (G)` | 4-8 | 太小方差大、太大采集慢 |
| `clip_range (ε)` | 0.1-0.2 | MoE 模型建议 0.1（更保守） |
| `kl_coef (β)` | 0.02-0.05 | KL 惩罚系数，防偏离 SFT 太远 |
| `lr` | 1e-6 ~ 5e-7 | 比 SFT 小 5-10 倍 |
| `epochs_per_rollout` | 2-4 | 每轮 rollout 数据训几遍 |
| `total_rollout_rounds` | 50-200 | 看 reward 收敛 |

## 5、训练稳定性与调试

### 5.1 MoE 模型的 RL 特殊问题

Qwen3-35B-A3B 是 MoE（Mixture of Experts）架构——8 个专家中每个 token 激活 3 个。

| 问题 | 原因 | 解法 |
|---|---|---|
| 路由跳变 | RL 梯度打到路由权重上，专家分配每轮都变 | **冻结路由层权重**（只训专家内部） |
| 负载不均衡加剧 | 某些专家被 RL 梯度“拉偏”，其他专家被冷落 | 加 `load_balancing_loss`（权重 0.01） |
| 梯度冲突 | 不同专家的梯度方向冲突 | 用更小的 `clip_range`（0.1 而非 0.2） |

**关键经验**：在 MoE 上跑 RL，**冻结路由层**是第一件要试的事。不冻结的话训练崩塌概率会显著增加。

### 5.2 KL 散度监控

KL 散度衡量当前 policy 偏离 SFT reference model 的程度：

| KL 范围 | 含义 | 应对 |
|---|---|---|
| < 0.5 | 几乎没学到新东西 | 提大 lr 或减小 `kl_coef` |
| 0.5 - 3.0 | 健康区间 | 正常继续 |
| 3.0 - 5.0 | 偏离较大，需关注 | 观察 reward 是否跟着涨 |
| > 5.0 | 危险：可能在 reward hack | 暂停、回退 checkpoint |
| > 10.0 | 崩塌信号 | 停止训练、排查 reward 设计 |

Globex 每轮 rollout 后打印 KL。连续 3 轮 `KL > 5.0` 就暂停。

### 5.3 训练崩塌的三个信号 + 应急

| 信号 | 表现 | 应急操作 |
|---|---|---|
| Reward 方差 → 0 | 所有轨迹得分一样（模型输出相同内容） | 回退到上一个好的 checkpoint |
| KL 一轮暴涨 > 10 | policy 突然偏离 reference | 回退 + 缩小 lr 一个量级 |
| 格式正确率从 98% 骤降到 < 90% | 模型“忘了”工具调用格式 | RL lr 太大；缩小到 1/5 或暂停 |

**应急原则**：RL 训练崩了**永远回退到上一个好的 checkpoint 重来**，不要试图“在崩塌的基础上修复”。

### 5.4 训练曲线正常形态 vs 异常形态

#### 正常形态

```text
Reward 均值：
  前 20 轮快速上升（从 0.3 → 0.5）
  后面缓慢爬升（0.5 → 0.6）

Reward P25/P75：
  区间逐渐收窄（模型行为趋于一致）

KL：
  前 10 轮快速上升到 1.5-2.0，然后稳定

格式正确率：
  始终 >= 96%
```

#### 异常形态 1——Reward hacking

```text
Reward 均值：
  一直上升到 0.8+（看似很好）

但人工抽查发现回答质量没提升。

原因：
  模型找到了刷分捷径。

应对：
  排查 reward 门禁是否缺失。
```

#### 异常形态 2——崩塌

```text
Reward 均值：
  突然从 0.5 跌到 -0.3

KL：
  同时暴涨到 8+

格式正确率：
  从 98% 骤降

应对：
  立刻回退 checkpoint。
```

## 6、从 SFT 到 RL 的过渡与迭代

### 6.1 什么时候从 SFT 切到 RL

**双条件同时满足：**

```text
格式正确率 >= 98%
AND
Rubric 均分 >= 65
```

不满足第一个条件就上 RL → RL 梯度会破坏格式，格式正确率可能更差。

不满足第二个条件就上 RL → reward 太稀疏，模型学不到东西。

### 6.2 SFT checkpoint 选哪个

- **Policy 初始化**：取满足双条件的 checkpoint 中 **Rubric 分最高**的那个。
- **Reference model**：用**同一个 checkpoint**，但冻结参数。GSPO 的 KL 惩罚就是相对于这个 reference 算的。

### 6.3 RL 迭代节奏

每轮 RL：

```text
Step 1: 采集 Rollout（256-1024 条轨迹）   — ~40 分钟
Step 2: 计算 Reward（含调 judge LLM）      — 已含在 Step 1 内
Step 3: 更新 Policy（GSPO 训 2-4 epoch）   — ~15 分钟
Step 4: 评测（50 条 eval + 格式指标）      — ~10 分钟
Step 5: 记录指标（reward / KL / 格式率）    — 秒级
```

```text
总计：~65 分钟 / 轮

50 轮：~54 小时（约 2.5 天）
200 轮：~220 小时（约 9 天）

推荐策略：
  先跑 50 轮看 reward 曲线，
  如果仍在上升则续跑到 100-200 轮，否则停。
```

### 6.4 RL 阶段评测

| 指标 | 怎么算 | 健康范围 |
|---|---|---|
| Win rate | 新 policy vs SFT baseline，judge 打分比较，取胜率 | >= 55%（显著） |
| Reward 均值 | 每轮 rollout 的平均 reward | 持续上升或趋平 |
| Reward P25/P75 | 分位数区间逐渐收窄 | 区间宽度 < 0.3 |
| KL | policy vs reference 的 KL 散度 | 0.5 - 3.0 |
| 格式正确率 | 每轮 eval 的格式指标 | >= 96%（底线） |

**发版标准：**

```text
win rate >= 60%
AND
格式正确率 >= 96%
AND
KL < 5.0
```

### 6.5 多轮 SFT → RL 迭代

RL 不是跑一次就结束。完整的季度迭代节奏：

```text
Q1：
  SFT v1（冷启动数据 550 条）
    → RL v1（50 轮）
    → 上线
    → 线上积累 RaR 高分轨迹
    → 新 SFT 数据

Q2：
  SFT v2（v1 高分轨迹 2000 条 + 蒸馏 500 条）
    → RL v2（100 轮）
    → 上线
    → 更多线上数据
    → 更多高分轨迹

Q3：
  SFT v3（v2 高分轨迹 5000 条）
    → RL v3（150 轮）
    → 上线
    → 数据飞轮进入稳态

持续：
  每月一次 SFT 增量更新
  每季度一次 RL 全量训练
```

每一轮的数据量和训练轮数都在涨——因为飞轮在持续积累高质量轨迹。

### 6.6 协同训练：RL 反哺 SFT

RL 训完的模型在线上跑出的轨迹，Rubric 分通常比纯 SFT 更高。这些高分轨迹反过来成为下一轮 SFT 的“更好的教师数据”：

```text
RL v1 线上
  → Rubric 分 75+ 的轨迹入库
  → 这批轨迹质量高于 SFT v1 用的训练数据
  → SFT v2 用这批数据训练
  → SFT v2 起点比 SFT v1 更高
  → RL v2 从更高起点出发
  → 推得更远
```

这就是第 8 章 §7 说的“数据飞轮”——在 SFT ↔ RL 两阶段之间不断螺旋上升。

## 本章小结

到这里，你应该能完整理解 Globex Agentic RL 训练的全流程：

1. **Agent RL 比通用 RLHF 更难**——Action space 大、Reward 延迟、环境非平稳，标准 PPO 直接用会方差大 + credit 难 + hacking 多。
2. **Reward 工程化**——五维公式可计算 + 归一化加权 + 终态为主过程为辅 + 三种 hacking 防御门禁。
3. **录制回放**让 Rollout 环境可复现、不依赖外部服务，是 Agent RL 训练的底座。
4. **GSPO**用序列级 geometric mean 比率 + 组内归一化优势，解决长序列方差大和 MoE 不稳定的问题。
5. **MoE 稳定性**——冻结路由层是第一件要试的事；KL 连续 > 5.0 就暂停；崩塌永远回退，不在崩塌 checkpoint 上硬修。
6. **季度迭代**——SFT → RL → 线上 → 新高分轨迹 → 新 SFT → 新 RL，形成螺旋上升。
7. **发版标准**——`win rate >= 60%` + `格式正确率 >= 96%` + `KL < 5.0`。
