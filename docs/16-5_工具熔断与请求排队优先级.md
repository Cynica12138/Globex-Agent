# 16-5 工具熔断与请求排队优先级

**本章课程目标：**
- 掌握工具熔断的三态模型（Closed → Open → HalfOpen），以及 Agent 场景下熔断后主 loop 的行为策略。
- 理解请求排队优先级的设计：按对话轮数分流 + 按用户等级排序 + 高峰期动态压缩。
- 掌握幂等性设计：Dict[thread_id, Task] + Checkpoint 防重跑 + 重复提交检测。
- 看清工具熔断、LoopDetector（第 14 章）、Token 预算（16-4 章）三者的关系——分别守不同维度的系统稳定性。

**学习建议：** 这一章解决两类"Agent 被拖垮"的问题：一类是外部工具不可靠（熔断），一类是请求量超过处理能力（排队）。两者一起保证"Agent 服务不会因为外部依赖挂了或流量突增而整体不可用"。

**对应代码分支：**`16-5-circuit-breaker-queue`

## 1、工具熔断：保护 Agent 不被外部依赖拖垮

### 1.1 问题：一个工具挂了，整个 Agent 跟着挂

Globex 依赖多个外部服务：亚马逊 API、Shopee API、速卖通 API、eBay API、Reranker 服务、三塔 Embedding 服务。任何一个挂了，不做处理会发生什么：
```text
亚马逊 API 响应超时（10s）
  → dispatch_tool fork 4 路，其中亚马逊那路一直等
  → 主 loop 等 dispatch_tool 返回 → 90s 超时才终止
  → 用户等了 90s 才看到"子任务超时"
  → 同时所有请求都在等亚马逊 → 并发连接池被占满
  → 其他正常平台的请求也开始排队
  → 整个系统雪崩

```

**工具熔断**的作用：一旦检测到某个工具持续失败，**立刻停止向它发请求**，让主 loop 知道"这个工具暂时不可用"，从而快速降级，不让整个系统被一个挂掉的服务拖崩。

### 1.2 三态模型
```text
┌─────────┐  失败率 > 30%  ┌────────┐  等待 5min  ┌──────────┐
│ Closed  │ ──────────────→│  Open  │ ───────────→│ HalfOpen │
│（正常）  │               │（熔断） │             │（试探）   │
└─────────┘               └────────┘             └──────────┘
     ↑                                                 │
     │            试探请求成功                           │
     └─────────────────────────────────────────────────┘
                  试探请求失败 → 回到 Open

```

| 状态  | 行为  |
|-------|-------|
| Closed  | 正常放行所有请求，同时统计失败率  |
| Open  | **拒绝所有请求**，直接返回"工具不可用"给主 loop  |
| HalfOpen  | 放一条探测请求过去，成功则回到 Closed，失败则回到 Open  |

### 1.3 完整实现
```python
# app/resilience/circuit_breaker.py
import asyncio
import time
from collections import deque
from enum import Enum
from typing import Callable, Awaitable, Any


class State(Enum):
    CLOSED = "closed"
    OPEN = "open"
    HALF_OPEN = "half_open"


class CircuitBreaker:
    """工具级熔断器。"""

    def __init__(
        self,
        tool_name: str,
        failure_threshold: float = 0.30,   # 失败率阈值
        window_size: int = 100,            # 滑动窗口大小
        recovery_timeout: float = 300.0,   # Open → HalfOpen 等待秒数
    ):
        self.tool_name = tool_name
        self.failure_threshold = failure_threshold
        self.window_size = window_size
        self.recovery_timeout = recovery_timeout

        self._state = State.CLOSED
        self._results: deque[bool] = deque(maxlen=window_size)  # True=成功, False=失败
        self._open_since: float = 0.0
        self._lock = asyncio.Lock()

    @property
    def state(self) -> State:
        if self._state == State.OPEN:
            # 检查是否到了试探时间
            if time.time() - self._open_since >= self.recovery_timeout:
                self._state = State.HALF_OPEN
        return self._state

    async def call(
        self,
        func: Callable[..., Awaitable[Any]],
        *args,
        **kwargs,
    ) -> Any:
        """通过熔断器调用工具。"""
        current_state = self.state

        if current_state == State.OPEN:
            # 熔断中，不发请求
            raise CircuitOpenError(
                f"工具 {self.tool_name} 已熔断，预计 "
                f"{int(self.recovery_timeout - (time.time() - self._open_since))}s 后试探恢复"
            )

        try:
            result = await func(*args, **kwargs)
            await self._record_success()
            return result
        except Exception as e:
            await self._record_failure()
            raise

    async def _record_success(self):
        async with self._lock:
            self._results.append(True)
            if self._state == State.HALF_OPEN:
                # 试探成功，恢复正常
                self._state = State.CLOSED

    async def _record_failure(self):
        async with self._lock:
            self._results.append(False)
            if self._state == State.HALF_OPEN:
                # 试探失败，回到 Open
                self._state = State.OPEN
                self._open_since = time.time()
            elif self._state == State.CLOSED:
                # 检查是否需要熔断
                if len(self._results) >= 10:  # 至少 10 个样本
                    failure_rate = self._results.count(False) / len(self._results)
                    if failure_rate >= self.failure_threshold:
                        self._state = State.OPEN
                        self._open_since = time.time()


class CircuitOpenError(Exception):
    """熔断器打开时抛出。"""
    pass

```

### 1.5 熔断后 Agent 的行为

熔断器抛出 `CircuitOpenError` 后，不是让 Agent 崩——而是把"工具不可用"作为一条 observation 注入主 loop：
```python
# app/tools/item_search.py（修改）
from app.resilience.breakers import get_breaker
from app.resilience.circuit_breaker import CircuitOpenError


@tool
async def item_search(query: str, platform: str, ...) -> ItemSearchOutput:
    breaker = get_breaker(f"item_search_{platform}")

    if breaker:
        try:
            result = await breaker.call(_actual_search, query, platform, ...)
            return result
        except CircuitOpenError as e:
            # 不抛异常，返回一个特殊结果让主 loop 知道
            return ItemSearchOutput(
                platform=platform,

                candidates=[ ],

                total_recall=0,
                truncated=False,
                error_message=str(e),  # 额外字段，告知主 loop
            )
    else:
        return await _actual_search(query, platform, ...)

```

主 loop 看到 `candidates=[ ]` + `error_message`，会在 Think 阶段自然处理：
```text
Think: 亚马逊 ItemSearch 返回了"工具已熔断"。
      已有 Shopee/速卖通/eBay 三个平台的结果。
      → 先用这三个平台的候选继续比价，不等亚马逊恢复。

```

## 2、请求排队优先级

### 2.1 问题：大请求把小请求堵住

Globex 同时接到两种请求：
- **正常请求**：3-8 轮对话，5-10s 搞定
- **大请求**：30+ 轮对话，可能 60s+

如果不区分，一个大请求占住一个 Worker 60s，后面 11 个正常请求全排队等。

### 2.2 双队列 + 优先级设计
```text
                     ┌─────────────────────┐
请求入口 ──→ 分类器 ──→│  正常队列（轮数 < 30）│ → Worker Pool A（8 个）
                     └─────────────────────┘
                     ┌─────────────────────┐
                  └──→│  大请求队列（轮数 ≥ 30）│ → Worker Pool B（4 个）
                     └─────────────────────┘

```

### 2.3 实现
```python
# app/resilience/request_queue.py
import asyncio
import heapq
from dataclasses import dataclass, field
from typing import Any


@dataclass(order=True)
class PrioritizedRequest:
    """按优先级排序的请求。priority 越小越优先。"""
    priority: int
    timestamp: float = field(compare=False)
    thread_id: str = field(compare=False)
    query: str = field(compare=False)
    user_id: str | None = field(compare=False, default=None)


class PriorityRequestQueue:
    """双队列 + 优先级调度。"""

    def __init__(self, normal_workers: int = 8, heavy_workers: int = 4):

        self._normal_queue: list[PrioritizedRequest] = [ ]


        self._heavy_queue: list[PrioritizedRequest] = [ ]

        self._normal_sem = asyncio.Semaphore(normal_workers)
        self._heavy_sem = asyncio.Semaphore(heavy_workers)

    def classify(self, dialog_turns: int) -> str:
        """按对话轮数分类。"""
        return "heavy" if dialog_turns >= 30 else "normal"

    async def enqueue(self, request: PrioritizedRequest, queue_type: str):
        """入队。"""
        if queue_type == "heavy":
            heapq.heappush(self._heavy_queue, request)
        else:
            heapq.heappush(self._normal_queue, request)

    async def acquire_worker(self, queue_type: str):
        """获取 Worker 许可。"""
        sem = self._heavy_sem if queue_type == "heavy" else self._normal_sem
        await sem.acquire()

    def release_worker(self, queue_type: str):
        """释放 Worker 许可。"""
        sem = self._heavy_sem if queue_type == "heavy" else self._normal_sem
        sem.release()


# 用户等级 → 优先级映射（越小越优先）
USER_PRIORITY = {
    "premium": 1,
    "standard": 5,
    "free": 10,
}


request_queue = PriorityRequestQueue()

```

### 2.4 高峰期动态调整

当正常队列排队数超过阈值时，从大请求队列"借"Worker：
```python
# app/resilience/request_queue.py（续）

async def dynamic_rebalance(self):
    """高峰期：压缩大请求 Worker，优先保正常请求。"""
    normal_pending = len(self._normal_queue)
    if normal_pending > 20:
        # 正常队列积压严重 → 大请求 Worker 从 4 降到 2
        self._heavy_sem = asyncio.Semaphore(2)
    elif normal_pending < 5:
        # 恢复
        self._heavy_sem = asyncio.Semaphore(4)

```

## 3、幂等性设计

### 3.1 问题：用户重复提交

用户在等待过程中刷新页面 → 前端重新发出 `POST /agent/run` → 同一条 query 可能被启动两次。

### 3.2 三层幂等保护

**第一层：active_tasks 检测**
```python
# app/api/server.py（已有，强调幂等逻辑）
active_tasks: dict[str, asyncio.Task] = {}

@app.post("/api/task")
async def create_task(req: TaskRequest):
    thread_id = req.thread_id or uuid.uuid4().hex

    # 幂等检测：同一 thread_id 已有活跃 Task → 直接返回
    existing = active_tasks.get(thread_id)
    if existing and not existing.done():
        return {"status": "already_running", "thread_id": thread_id}

    # 新建 Task
    task = asyncio.create_task(_runner(req, thread_id))
    active_tasks[thread_id] = task
    return {"status": "started", "thread_id": thread_id}

```

**第二层：Checkpoint 防重跑**

如果服务重启，`active_tasks` dict 被清空。用户再发请求：
- Checkpoint（Redis）里有这个 thread_id 的最新状态
- LangGraph 从 Checkpoint 恢复 → 继续执行，不从头跑

**第三层：请求指纹去重**

防止用户换 thread_id 但发同一条 query：
```python
# app/resilience/dedup.py
import hashlib
import time

_recent_requests: dict[str, float] = {}  # fingerprint → timestamp
DEDUP_WINDOW = 5.0  # 5 秒内同一 fingerprint 视为重复


def is_duplicate(user_id: str | None, query: str) -> bool:
    fp = hashlib.md5(f"{user_id}:{query}".encode()).hexdigest()
    now = time.time()

    # 清理过期指纹
    expired = [k for k, t in _recent_requests.items() if now - t > DEDUP_WINDOW]
    for k in expired:
        del _recent_requests[k]

    if fp in _recent_requests:
        return True  # 重复

    _recent_requests[fp] = now
    return False

```

## 4、三个稳定性维度的关系

### 4.1 一张图看清三者的守护边界
```text
                    ┌──────────────────────────────┐
                    │     用户请求进来              │
                    └──────────┬───────────────────┘
                               ↓
                    ┌──────────────────────────────┐
                    │  请求排队优先级（本章 §2）     │  ← 守【系统容量】
                    │  不让大请求堵小请求            │
                    └──────────┬───────────────────┘
                               ↓
                    ┌──────────────────────────────┐
                    │  Token 预算（16-4 章）         │  ← 守【成本】
                    │  单请求不超预算                │
                    └──────────┬───────────────────┘
                               ↓
                    ┌──────────────────────────────┐
                    │  LoopDetector（第 14 章）      │  ← 守【Agent 行为】
                    │  不让 Agent 自己打转           │
                    └──────────┬───────────────────┘
                               ↓
                    ┌──────────────────────────────┐
                    │  工具熔断（本章 §1）           │  ← 守【外部依赖】
                    │  不让坏工具拖垮整个系统        │
                    └──────────────────────────────┘

```

### 4.2 四者的协同场景
```text
场景：亚马逊 API 连续超时，同时涌入大量请求

1. 工具熔断 → 亚马逊 ItemSearch 进入 Open 状态 → Agent 自动跳过亚马逊
2. 跳过后 Agent 只查 3 个平台 → token 消耗减少 → Token 预算压力减轻
3. 请求排队 → 溢入的请求按优先级排队 → 不让 Worker 被打满
4. LoopDetector → 如果 Agent 因为少了一个平台数据反复重试 → 注入收敛提示

四层一起工作 = 系统在外部服务异常 + 流量突增时仍然可用

```

## 5、熔断状态的持久化与多实例共享

### 5.1 单实例问题

16-1 章只有一个 Agent 实例时，熔断器状态存在内存里没问题。但多实例部署时：
```text
实例 A 检测到亚马逊 API 挂了 → 本地熔断
实例 B 不知道 → 继续向亚马逊发请求 → 被拖慢

```

### 5.2 Redis 共享状态
```python
# app/resilience/shared_breaker.py
import jsonimport time
from app.utils.redis_client import redis


class SharedCircuitBreaker(CircuitBreaker):
    """多实例共享的熔断器，状态存 Redis。"""

    async def _sync_state_to_redis(self):
        key = f"breaker:{self.tool_name}"
        await redis.set(key, json.dumps({
            "state": self._state.value,
            "open_since": self._open_since,
            "failure_count": self._results.count(False),
            "total_count": len(self._results),
        }), ex=600)  # 10 分钟过期

    async def _load_state_from_redis(self):
        key = f"breaker:{self.tool_name}"
        data = await redis.get(key)
        if data:
            info = json.loads(data)
            self._state = State(info["state"])
            self._open_since = info["open_since"]

```

每次状态变更时同步到 Redis，每次请求前从 Redis 读一次（加本地缓存 5s 减少 Redis 压力）。

```python
            f"[熔断] 工具 {self.tool_name} 已熔断，"
            f"失败率 {self._failure_rate():.0%}，"
            f"预计 {self.recovery_timeout}s 后试探恢复"

```

### 6.2 看板指标

| 指标  | 含义  | 告警阈值  |
|-------|-------|-------------|
| 各工具当前状态  | Closed / Open / HalfOpen  | 任何工具 Open  |
| 各工具失败率  | 滑动窗口内失败比例  | > 20%  |
| 熔断触发次数/小时  | 每小时进入 Open 的次数  | > 5  |
| 恢复成功率  | HalfOpen → Closed 的比例  | < 50%  |
| 正常队列排队数  | 当前等待处理的正常请求  | > 20  |
| 大请求队列排队数  | 当前等待处理的大请求  | > 10  |

**本章小结：**

到这里，Globex 有了完整的外部依赖保护和流量调度机制：
1. **工具熔断三态模型**：Closed → Open → HalfOpen，滑动窗口失败率 > 30% 触发，5 分钟后试探恢复。
2. **熔断后 Agent 行为**：返回特殊结果（不抛异常），主 loop 在 Think 阶段自然降级处理。
3. **双队列 + 优先级**：按对话轮数分流，同队列按用户等级 heapq 排序，高峰期动态压缩大请求 Worker。
4. **三层幂等**：active_tasks 检测 + Checkpoint 防重跑 + 请求指纹去重。
5. **多实例共享**：熔断状态存 Redis，所有实例同步感知。
6. **四维稳定性**：排队守容量 / Token 预算守成本 / LoopDetector 守行为 / 工具熔断守依赖——四层一起才是完整防线。
